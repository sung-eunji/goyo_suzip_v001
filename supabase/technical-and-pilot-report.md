## 1. 한눈에 보는 현재 상태

고요수집은 하루의 몰아침과 몸의 감각, 사용자가 들인 고요와 뜻밖에 만난 고요를 기록하는 웹앱입니다. 기술적으로는 브라우저 앱이 Supabase Auth와 Postgres에 직접 연결하며, 사용자별 권한은 RLS로 분리합니다.

현재 구현된 핵심 흐름은 익명 시작 → 날짜별 감각 기록 → 주·월간 흐름 보기 → 원할 때 이메일 계정으로 전환입니다. 익명 사용자는 브라우저마다 별도 계정이므로, 여러 브라우저에서 기록을 이어 쓰려면 이메일 계정으로 전환하고 로그인해야 합니다. 닉네임은 표시명이며 계정 복구 수단이 아닙니다.

현재 앱은 개인 기록과 분석에 필요한 일부 신호를 수집하지만, 파일럿 운영에 필요한 참여 동의, 실험 결제, 리마인더, 운영자 체크인, 종료 피드백 설문은 아직 제품 흐름에 연결되어 있지 않습니다.

## 3. 현재 데이터 구조

### 3.1 사용자 및 설정

| 테이블     | 주요 데이터                                                                                                                         | 용도                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `profiles` | `id`, `nickname`, `nickname_key`, `role`, `subscribed`, `cohort`, `is_anonymous`, `converted_at`, `research_consent`, `analysis_id` | Auth 사용자와 앱 프로필 연결, 운영 상태, 가명 분석 키   |
| `settings` | `theme`, `reminder_at`, `prefs`                                                                                                     | 사용자 UI 설정. 분석용 일일 응답은 여기에 저장하지 않음 |

사용자 기본키는 `profiles.id = auth.users.id`입니다. `nickname_key`는 공백 정리된 닉네임이며 유일 인덱스로 중복 표시명을 막습니다. 같은 닉네임 자동 연결은 계정 탈취 위험 때문에 하지 않습니다.

### 3.2 마스터 데이터

| 테이블                  | 현재 목적                                                             |
| ----------------------- | --------------------------------------------------------------------- |
| `vessel_types`          | 산책, 독서, 호흡 등 고요를 담는 활동 분류 축                          |
| `sensation_options`     | 코드형 몸 감각 선택지의 기준 테이블                                   |
| `body_response_options` | 고요 뒤 몸의 응답/풀림 기준 테이블                                    |
| `forecast_event_types`  | 마감, 출장, 아이 일정 등 예보 일정 분류 선택지                          |

### 3.3 약속과 일정 예보

| 테이블                | 키/내용                                                   | 분석 질문                                                          |
| --------------------- | --------------------------------------------------------- | ------------------------------------------------------------------ |
| `promises`            | `user_id`, 월, 원문, 순서, 활성 여부, 선택적 `vessel_key` | 사용자는 어떤 고요를 원하고 약속하는가? 약속한 행동은 실천되는가?  |
| `forecast_day_events` | 사용자, 날짜, 일정 유형, 기타 설명                       | 어떤 일정이 예정되어 있는가?                                      |
| `forecasts`           | 사용자, 날짜, `level` 0–4                                 | 사용자가 고른 급증 예상 단계                                      |

일정 유형과 급증 정도는 별도로 입력합니다. 급증 단계는 0/25/50/75/100%의 다섯 표시값(기준 낮음 0% + 25%씩 증가하는 네 단계)으로 선택합니다. `v_forecast_score`는 `forecasts.level × 25`로 점수를 계산하고, 달력 칸도 같은 비율로 채워집니다. “기타” 일정 설명은 `forecast_day_events.event_note`에 원문으로 저장합니다.

### 3.4 일일 기록

| 테이블                 | 주요 필드                                                          | 데이터 의미                                       |
| ---------------------- | ------------------------------------------------------------------ | ------------------------------------------------- |
| `entries`              | `user_id`, `local_date`, `tz`, `surge`, `no_stillness`, `day_note` | 하루의 몰아침 강도, 고요 없음, 자유 메모          |
| `entry_promise_checks` | `entry_id`, `promise_id`, `done`, `minutes`                        | 월간 약속 중 그날 실천한 항목                     |
| `entry_sensations`     | `entry_id`, `category`, `option_key` 또는 `text_raw`               | 조임/흐름/풀림 몸 감각 태그                       |
| `encounters`           | `entry_id`, `text_raw`, `minutes`, `vessel_key`                    | 계획하지 않았지만 찾아온 고요의 순간과 시간       |
| `encounter_responses`  | `encounter_id`, `response_key`                                     | 그 순간 뒤 몸의 반응                              |
| `survey_responses`     | `survey_key`, `answers` JSONB                                      | 날짜별 니즈, 바라는 변화, 해결감과 버전 변경 설문 |

`entries`는 `(user_id, local_date)` 유일 제약으로 하루 한 행입니다. 몸의 느낌이나 고요의 순간은 정규화된 자식 행으로 분리됩니다. 사용자가 자유롭게 적은 문장은 분류를 하더라도 원문을 보존하는 것을 원칙으로 합니다.

### 3.5 회고, 운영, 이벤트

| 테이블           | 현재/예정 역할                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `weekly_reviews` | 주간 회고 텍스트와 그룹 공유 선택                                                            |
| `events`         | 화면/기능 사용 이벤트. 테이블은 있으나 현재 앱에서 이벤트를 기록하지 않음                    |
| `program_days`   | 코호트별 프로그램 일자·신체 시스템·프롬프트 키. 원격에는 있으나 현 앱 화면에서 연결되지 않음 |

### 3.6 분석 뷰

- `v_day`: 일별 기록, 실천한 약속 수, 만남 횟수/시간, 조임·풀림 감각 수를 한 행으로 요약
- `v_forecast_score`: `forecasts.level × 25`로 일별 예보 점수를 계산

이 뷰는 시각화/CSV에서 일별 원천 테이블을 반복 조인하지 않도록 돕습니다.

## 4. 사용자 입장에서 현재 동작

1. **처음 방문**: 새 닉네임을 등록합니다. `is_nickname_available()`이 중복 여부를 확인하고, 사용 가능할 때 Supabase Auth가 브라우저용 UUID를 만든 뒤 같은 ID로 `profiles` 프로필을 생성합니다.
2. **이번 달 준비**: 캘린더에서 앞으로의 일정 유형을 표시하고, 지키고 싶은 고요 약속을 1~3개 정합니다.
3. **오늘 기록**: 몰아침 게이지, 오늘 상황 메모, 지킨 약속, 찾아온 고요와 시간, 몸 감각, 오늘 필요한 변화/니즈, 해결감을 기록합니다. “고요 없음”도 유효한 기록입니다.
4. **저장**: `entries`와 관련 자식 테이블, 날짜별 `survey_responses`에 저장합니다.
5. **돌아보기**: 오늘/월간은 무료 화면으로 제공하고, 주간/흐름 탭은 현재 구독 여부에 따라 잠금 처리됩니다.
6. **기록 보존**: 익명 사용자가 대시보드의 “다른 브라우저에서 기록 이어보기 · 회원가입하기”에서 이메일/비밀번호를 연결하면 같은 Auth ID를 유지합니다. 다른 브라우저에서는 해당 이메일로 로그인합니다.

실제 결제는 연결되어 있지 않고, 익명 사용자 계정은 브라우저 저장소/세션을 잃으면 복구할 수 없습니다. 사용자가 계정 전환을 하지 않은 채 브라우저를 바꾸면 기존 기록으로 자동 연결되지 않습니다.

## 5. 운영자/관리자 입장에서 현재 동작

- `profiles.role = 'admin'`인 계정은 관리자 탭을 봅니다.
- 관리자 화면에서 참가자별 가입일, 기록일수, 평균 몰아침, 약속 실천, 만남 시간, 고요 없던 날, 마지막 기록일을 요약하고 일별 집계 CSV를 내려받습니다.
- RLS는 `is_admin()` 함수로 관리자를 판별하며, 관리자에게 읽기 권한을 주되 일반 사용자의 쓰기 검증은 자기 `user_id`로 제한합니다.
- 프로필 보호 트리거는 일반 사용자가 `role`, `subscribed`, `cohort`, 연구 동의 관련 보호 컬럼 등을 임의로 바꾸지 못하게 막습니다.
- 현재 운영 화면에는 코호트/결제 상태 관리, 참가자에게 체크인 보내기, 설문 링크 발송, 피드백 열람/분류 워크플로가 없습니다. 운영자는 Supabase 대시보드와 CSV를 함께 봐야 합니다.

## 6. 현재 구현된 접근 제어와 DB 자동화

### RLS

모든 원격 기본 테이블은 RLS가 활성화되어 있습니다. 개인 데이터는 기본적으로 `user_id = auth.uid()` 조건으로 분리하고, 관리자는 읽을 수 있도록 정책이 구성되어 있습니다. 마스터 선택지는 인증 사용자에게 읽기를 허용하고 관리자만 수정하도록 되어 있습니다.

현재 정책은 PostgreSQL 기본값인 permissive입니다. 현재는 테이블별 소유권 정책의 조건이 동작하지만, 향후 익명 사용자에 대한 특정 쓰기 제한을 추가할 때는 permissive 정책의 OR 결합을 고려해 정책을 설계·검증해야 합니다.

### 함수와 트리거

원격 DB에서 확인된 함수:

- `public.is_admin()`: 프로필 `role`로 관리자 여부를 반환
- `public.profiles_guard_privileged_columns()`: 비관리자의 프로필 권한 컬럼 변경/삽입을 거부하는 트리거 함수
- `public.is_nickname_available(text)`: 닉네임 원문이나 사용자 정보를 노출하지 않고 사용 가능 여부(boolean)만 반환. `anon`과 `authenticated`에 실행 권한이 부여됨

원격 DB에서 확인된 트리거:

- `profiles_guard_privileged_columns_trg`
- `profiles`의 `BEFORE INSERT`와 `BEFORE UPDATE`에서 실행

현재 자동 트리거로 구현되지 않은 항목:

- `updated_at` 자동 갱신
- 닉네임 정규화 자동 처리
- 자유 텍스트의 자동 분류
- 하루 저장 전체를 원자적으로 처리하는 `save_day()` RPC

### 지금 데이터가 충분한가?

현재 일별 입력은 “그날의 상태, 몸의 감각, 고요 경험, 그날 바란 변화와 해결감”을 보기 시작할 수 있습니다. 그러나 다음 질문에 답할 데이터는 아직 부족합니다.

- 사용자의 장기 핵심 니즈와 우선순위
- 프로그램 전후의 기준선 변화
- 어떤 지원/체크인이 도움이 되었는지와 부담이 되었는지
- 참여가 끊긴 이유
- 가격별 지불 의향과 실제 결제/환불
- 피드백에서 원하는 주제와 수신 채널
- 파일럿 후에도 유지하고 싶은 행동

즉, 질문하신 분석 데이터의 방향은 일부 화면 입력으로 반영됐지만, 전부 구조화되거나 운영 중인 상태는 아닙니다. 특히 `user_intents` 같은 장기 니즈 엔터티는 현재 스키마에 없고, 날짜별 설문 응답만 있습니다.

## 8. 파일럿에서 사용자를 느슨해지지 않게 돕는 제안

목표는 사용자를 죄책감으로 압박하는 것이 아니라, **작은 약속을 하고 누군가가 실제로 관심을 두고 있다는 것을 느끼게 하는 것**입니다. 지속성 실험과 평가 데이터도 더 신뢰할 수 있습니다.

### 권장 운영 구조: 3주, 유료 소규모 코호트

1. **가입 전 약속**: “하루 2분 기록, 주 1회 짧은 회고, 종료 피드백”처럼 요구를 구체적으로 공개합니다. 빈도와 예상 시간을 미리 합의합니다.
2. **시작일 기준선**: 지금의 몰아침, 바라는 변화, 현재 쓰는 회복 방법, 이번 실험에서 기대하는 것을 간단히 받습니다.
3. **주간 체크인**: 참가자가 동의한 채널에서 주 1회만 발송합니다. 예: “이번 주 기록을 못 한 날도 괜찮아요. 가장 바빴던 날 하나와 도움이 된 순간 하나만 돌아봐 주세요.”
4. **진행 가시성**: 개인 대시보드에 기록한 날/주간 회고 완료 상태를 본인에게 보여줍니다. 공개 순위, 연속일수 경쟁, 누락 경고는 파일럿 초기에는 사용하지 않습니다.
5. **운영자 존재감**: 운영자가 주 1회 공통 인사이트나 짧은 음성/텍스트를 공유하고, 희망자에 한해 10분 면담 또는 비공개 피드백을 제공합니다.
6. **종료 회고**: 시작 전 기대와 종료 후 경험을 비교하고, 피드백을 제품 개선에 사용할 범위와 익명화 방식을 확인합니다.

### 인증/책임감 방식 옵션

| 방식                               | 압박감 | 운영 부담 | 추천                                 |
| ---------------------------------- | -----: | --------: | ------------------------------------ |
| 주 1회 자기 점검 + 자동 진행 표시  |   낮음 |      낮음 | 기본                                 |
| 운영자가 동의받은 주간 체크인 발송 |   중간 |      중간 | 파일럿 추천                          |
| 2인 버디, 서로 격려 메시지         |   중간 |      중간 | 참가자가 원할 때 선택                |
| 소그룹 주간 모임/오피스아워        |   중간 |      높음 | 핵심 참가자 소수                     |
| 연속 기록 공개 순위/누락 패널티    |   높음 |      낮음 | 비추천: 수치 왜곡·수치심·이탈 가능성 |

“인증”은 완료 증명을 요구하기보다 참여자 스스로 정한 작은 약속과 주간 회고를 확인하는 정도가 적절합니다. 치료 효과나 생산성 향상을 보장하지 말고, 이 실험은 개인의 감각을 관찰하는 제품 실험이라고 분명히 합니다.

## 9. 5,000원 파일럿과 피드백 설계

### 개인사업자 커뮤니티 파일럿 제안

- 참가자: 커뮤니티에서 모집한 소규모 성인 개인사업자 그룹
- 기간: 3주 권장 (시작 설문 + 3주 사용 + 종료 인터뷰)
- 가격: 5,000원은 “유료 베타 참여 및 피드백 교환”의 파일럿 가격으로 명시
- 제공: 3주 접근, 주 1회 운영자 체크인, 종료 후 요약 인사이트/제품 변경사항 공유
- 데이터 동의: 서비스 이용 동의와 연구/제품 분석 동의를 구분하고, 참여 거부/중도 종료/삭제 요청 경로를 알립니다.
- 결제: 실제 결제 시스템이 아직 없으므로 수동 결제를 한다면 운영자 장부와 앱 분석 ID를 분리하고, 민감한 결제정보를 앱 DB에 저장하지 않습니다.

### 꼭 물어볼 피드백 질문

1. 시작 전, 일상에서 가장 해결하고 싶었던 순간/상태는 무엇이었나요?
2. 3주 뒤 그 상태가 어떻게 달라졌나요? 달라지지 않았다면 무엇이 방해했나요?
3. 기록 중 어떤 입력이 나를 이해하는 데 실제로 도움이 됐나요?
4. 너무 번거롭거나 불편해서 건너뛴 입력/화면은 무엇이었나요?
5. “고요”를 담는 활동 중 계속하고 싶은 것은 무엇이고, 이유는 무엇인가요?
6. 운영자의 주간 체크인 빈도와 말투가 적절했나요? 부담스럽거나 부족했나요?
7. 이 프로그램을 누구에게 권하고 싶나요? 권하지 않는다면 이유는 무엇인가요?
8. 유료로 계속한다면 어떤 결과/지원이 있어야 가치 있다고 느끼나요?
9. 5,000원 지불은 어떤 점에서 적절/부적절했나요?
10. 다음 버전에서 꼭 고칠 한 가지와 유지할 한 가지는 무엇인가요?

피드백을 “만족했나요?” 하나로 끝내지 말고, 구체적 사용 장면, 변화의 예, 실패/중단 이유, 가치와 가격 근거를 수집합니다. 긍정 평가만 유도하지 않도록 부정 경험을 먼저 물을 수 있습니다.

### 5,000원 → 9,900원 → €2/$2 단계

- **1단계: 커뮤니티 유료 파일럿 5,000원**: 작은 코호트로 사용성, 실제 반복 사용, 운영자가 제공해야 하는 지원량을 확인합니다.
- **2단계: 인스타그램 판매 9,900원**: 파일럿에서 확인한 한 가지 구체적 효용과 대상 고객을 중심으로 릴스/랜딩 메시지를 실험합니다. 파일럿 참가자와 일반 구매자를 코호트로 분리해 비교합니다.
- **3단계: LinkedIn 영문/유럽·영어권 실험**: 영문 카피, 시간대/날짜, 단위·문화적 표현을 현지화합니다. €2와 $2는 같은 가격으로 취급하지 말고 현지 결제 수수료, 세금, 구매력, 통화별 전환율을 별도로 봅니다.

가격은 단계별로 한 번에 여러 기능·대상·메시지를 바꾸지 말고, 코호트별로 가격과 제안을 기록합니다. “가격이 싸서 샀는지”와 “제품이 필요해서 샀는지”를 구분하기 위해 실제 전환율, 완료율, 환불, 종료 인터뷰를 함께 봅니다. 아직 결제 연동과 가격 실험 로깅은 구현되지 않았습니다.

## 10. 파일럿에서 권장하는 성공 지표

초기에는 단일 북극성 지표를 확정하기보다 아래를 함께 봅니다.

- 활성화: 가입 후 첫 기록/첫 월간 약속까지 도달한 비율
- 참여 지속: 1주차·2주차·3주차 기록 일수와 주간 회고 완료율
- 기록 부담: 입력에 걸린 체감 시간, 건너뛴 항목, 중도 이탈 이유
- 가치: 시작 기대 대비 종료 시 변화, “계속 쓸 이유”의 자유 응답
- 운영 부담: 참가자 1명당 주간 운영자 시간, 체크인 응답률
- 사업성: 모집 전환율, 유료 구매율, 환불, 가격 수용성, 추천 의향
- 안전/신뢰: 불편한 알림/압박 신고, 데이터 삭제·동의 철회 요청

기록하지 않은 날은 자동으로 실패나 낮은 의지로 해석하지 않습니다. 빠진 데이터는 이탈 신호일 수 있지만, 여행·돌봄·바쁜 업무 등 원인이 다를 수 있어 종료 피드백으로 맥락을 확인합니다.

## 11. 관리자 데이터 흐름

```text
참가자 브라우저
  -> Supabase Auth (익명 UUID 또는 이메일 계정)
  -> profiles
  -> promises / forecast_day_events
  -> entries
      -> entry_promise_checks
      -> entry_sensations
      -> encounters -> encounter_responses
  -> survey_responses (daily:<date>)
  -> v_day / v_forecast_score
  -> 관리자 참가자 요약 및 CSV
```

현재 관리자 화면은 `profiles`와 `v_day`로 개인별 집계를 만들고, CSV는 일별 집계 데이터 중심입니다. 연구용 내보내기에서는 `nickname`과 Auth UUID 대신 `analysis_id`를 사용하도록 개선하는 것을 권장합니다. `research_consent`가 false인 사용자는 연구 분석용 내보내기에서 제외해야 합니다.

## 12. 현재 확인한 원격 DB 상태

2026-10-03 원격 카탈로그 조회 결과:

- 기본 테이블: 18개
- 뷰: `v_day`, `v_forecast_score` 2개
- public 함수: `is_admin()`, `profiles_guard_privileged_columns()` 2개
- 트리거: `profiles_guard_privileged_columns_trg` 1개 (BEFORE INSERT와 BEFORE UPDATE 이벤트)
- 확인된 건수: `profiles` 2, `promises` 14, `forecast_day_events` 2
- 확인된 건수: `entries` 0, `forecasts` 0, `survey_responses` 0, `events` 0, `program_days` 0
- 원격에는 `forecast_event_types`, `forecast_day_events`, `program_days`가 존재
- 2026-10-03 후속 업데이트: 프로필의 `gender` 허용값을 `man`, `woman`, `prefer_not_to_say`로 제한하는 마이그레이션 적용
- 필드별 저장 위치와 기록 날짜 의미는 [데이터 사전](data-dictionary-and-dates.md)에 정리

원격 DB에는 로컬 `supabase/schema.sql`에 아직 정의되지 않은 테이블/뷰가 있습니다. 즉 로컬 스키마 파일만으로 원격 환경 전체를 재현할 수 없는 **스키마 드리프트** 상태입니다.

또한 앱의 `fetchJournal()`에서 `encounter_responses.encounter_id`를 `entries.id` 목록으로 필터링하는 코드 경로가 보여, 저장된 응답을 다시 불러오지 못할 수 있습니다. 일일 저장도 여러 REST 요청으로 나뉘어 일부 성공/일부 실패가 가능한 상태입니다. 파일럿 사용자 모집 전에 응답 조회 필터와 스키마 동기화, 원자적 저장을 점검해야 합니다.

## 13. 우선순위별 다음 기술 작업

### 파일럿 시작 전 필수

1. 원격 DB와 `supabase/schema.sql`을 일치시킵니다. 예보 이벤트 테이블/시드와 `program_days`를 정식 마이그레이션으로 관리합니다.
2. 일별 저장 경로를 `save_day()` RPC 또는 동등한 트랜잭션으로 묶어 부분 저장을 방지합니다.
3. `encounter_responses` 조회에서 실제 encounter ID 목록을 사용하고, 저장→새로고침→복원 통합 테스트를 추가합니다.
4. `promises` 활성 행의 사용자/월/position 중복을 DB 제약으로 막습니다.
5. 앱 저장 요청에서 각 자식 테이블 에러를 검사하고 사용자에게 실패 상태를 표시합니다.
6. 개인정보/연구 동의를 별도로 받고, `analysis_id` 기반 익명 내보내기와 데이터 삭제 절차를 마련합니다.
7. 앱/관리자 권한에 `research_consent`를 반영하고 파일럿 데이터 보존 기간을 정합니다.

### 파일럿 기간 중 권장

- 코호트별 시작/종료 설문을 `survey_responses`에 버전 키로 기록
- 체크인 발송/열람/완료를 `events`에 최소 이벤트로 기록
- 동의한 채널과 빈도만 저장하고 알림 발송 이력/중단 선택 제공
- 운영자용 코호트/피드백 요약 화면
- 가격, 제안 문구, 결제/환불은 앱 분석 데이터와 분리된 실험 메타데이터로 추적

### 이후

- RLS/권한 자동 테스트 및 백업/복원 절차
- 이메일 인증/비밀번호 재설정 UX
- 이벤트 기반 funnel/retention 분석
- 영문 로캘, 유럽 날짜/시간대와 통화별 결제
- Stripe/Toss 등 결제 웹훅은 Edge Function에서 처리하고 클라이언트가 `subscribed`를 직접 변경하지 못하게 유지

## 14. 결론

현재 제품은 “일일 자기 관찰”의 핵심 루프와 정규화된 분석 저장 구조를 갖췄습니다. 현재 DB는 앱의 몰아침·고요 데이터 분석을 시작할 토대는 있지만, 파일럿 프로그램의 운영 데이터(참여 동의, 체크인, 종료 피드백, 결제, 가격 실험)와 장기 니즈 프로필은 아직 부족합니다.

권장 순서는 **스키마 드리프트/일일 저장 안정성 수정 → 3주·5,000원 소규모 파일럿 → 종료 피드백으로 효용과 운영 부담 검증 → 9,900원 인스타그램 제안 실험 → 영어권에서 별도 현지화/가격 실험**입니다. 참여 압력은 공개 경쟁이나 벌점보다, 참가자가 미리 동의한 주간 체크인과 운영자의 실제 관심으로 만듭니다.
